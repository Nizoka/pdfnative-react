# Reproducible output

The same document, rendered on any host, at any time, in any time zone, gives
the same bytes — once its creation instant is pinned.

_Applies to pdfnative-react v1.3.0 · pdfnative 1.8.0. Verified on 2026-09-22 against the source tree._

Runnable: [`samples/quality/reproducible.tsx`](../samples/quality/reproducible.tsx).

## The promise

Unencrypted `pdfnative` output is a pure function of its inputs plus one date.
Three engine facts make the promise hold since 1.8.0:

1. **Every date is written in UTC** — `/CreationDate` and `/ModDate` end in `+00'00'`, the XMP dates in `+00:00` — whatever the host's `TZ`.
2. **The trailer `/ID` derives from the creation instant** (and the content), not from a random source.
3. **The `{date}` header/footer placeholder follows the creation instant**, not the wall clock.

Pin the instant and the bytes repeat — on Linux, Windows and macOS, which is
what this repository's CI proves on its own sample set.

## TL;DR

```tsx
<Document title="Report" creationDate={new Date('2026-01-01T00:00:00Z')} header={{ right: 'Built {date}' }}>
```

```json
{ "title": "Report", "creationDate": "2026-01-01T00:00:00Z", "header": { "right": "Built {date}" }, "blocks": [] }
```

## Ways to pin, and their precedence

| Precedence | Where | Scope |
|---|---|---|
| 1 | `<Document creationDate>` · `DocSpec.creationDate` · `RenderOptions.layout.creationDate` | This document. A `Date`, or an ISO 8601 string (the JSON form); an unparseable string is an `E_INPUT` error at compile time — never a silent fallback to the clock |
| 2 | `setDefaultCreationDate(date)` (re-exported from the engine) | Every document rendered by this process without its own pin; `setDefaultCreationDate(null)` restores the clock; `getDefaultCreationDate()` reads it |
| 3 | nothing | The wall clock — the historical behaviour; two renders differ in their dates and `/ID` |

**The library reads no environment variable.** A build pipeline that exports
`SOURCE_DATE_EPOCH` pins the instant explicitly — one line in the caller:

```ts
const epoch = process.env.SOURCE_DATE_EPOCH;
if (epoch) setDefaultCreationDate(new Date(Number(epoch) * 1000));
```

The repository's own scripts do exactly that for the sample generator
(`scripts/helpers/pin-creation-date.mjs`); a `SOURCE_DATE_EPOCH` in your shell
affects them, never your application.

## What is not covered, by design

- `layout.encryption` — a fresh file key, salts and IVs on every build (ISO 32000-1 §7.6). An encrypted document is never byte-stable; compare it after decryption, or compare the unencrypted render.
- Anything done to the bytes afterwards — a signature, a timestamp, an incremental update — belongs to the engine and carries its own clock.
- `renderToResponse({ etag: true })` hashes the rendered bytes, so its validator is stable across hosts only when the document is pinned; unpinned, it changes on every render (a validator derived from your data stays cheaper — see [SERVER.md](SERVER.md)).

## Proving it

```ts
import { createHash } from 'node:crypto';
const sha256 = (b: Uint8Array) => createHash('sha256').update(b).digest('hex');

sha256(renderToBytes(doc)) === sha256(renderToBytes(doc));   // true, in any zone, on any host
```

Two processes under different `TZ` values give the same result; the sample
prints both hashes and the `/CreationDate` string.

## How the repository proves it

- `tests/reproducible.test.tsx` — the pin reaches `/CreationDate`, the `{date}` placeholder and therefore the bytes; the precedence order; UTC without a pin.
- `tests/regression/reproducible-build.test.ts` — the **built** package renders one document in two child processes under `TZ=Pacific/Kiritimati` and `TZ=America/Los_Angeles`: same bytes, dates in `+00'00'`, with the prop and with `setDefaultCreationDate` alone.
- `tests/regression/baselines/samples.sha256.json` — the SHA-256 of every sample, generated by `npm run test:generate` (each sample in its own process, instant pinned to `2026-01-01T00:00:00Z`, `TZ=UTC`) and held by `npm run verify:samples` on Linux, Windows and macOS (`sample-regression.yml`, a required check). The baseline is a chain: every entry names the release whose output it is (`since`), and a rebaseline is a declared decision in the release note, never a silent refresh.
