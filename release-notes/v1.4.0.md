# pdfnative-react v1.4.0

<!-- GitHub Release title: v1.4.0 - Right-to-left text, spot colours, the joint PDF/A + PDF/X claim, JPEG 2000, 32 scripts -->

_Released 2026-11-01_

The engine-alignment release for **pdfnative 1.9.0**. Every 1.9.0 authoring
capability reaches both doors — JSX props and the `DocSpec` grammar with its
JSON Schema — through the single registry: right-to-left documents
(`direction`), spot colours (`print.spotColours`, `{ spot }` and `{ inks }`
colour values), the joint PDF/A-2 + PDF/X-4 claim, per-value chart colours and
optional series labels, JPEG 2000 images, and five more Indic scripts (32 in
all). Four lint rules carry the engine's new throws one tier earlier, the
diagnostics channel grows to thirteen codes, and the repository takes the
1.9.0 engineering standard of the engine: the previous release's test suite
replayed against the current sources, frozen 1.3.0 captures beside the 1.2.0
ones, a workflow-lint check, a four-job release pipeline with blocked egress,
seven required checks on three operating systems.

What did **not** change: 19 components, 14 block kinds, 6 error codes, 7
schema subjects, the defaults, and the bytes of every document that embeds no
font and sets no right-to-left text — the 27 base-14-only samples of the
baseline keep their 1.3.0 hashes.

## Compatibility — read this first

No public API was removed or renamed; every new behaviour is opt-in. The
v1.3.0 test suite passes against 1.4.0 (`npm run compat:previous`: 24 files,
403 passing cases; fifteen exclusions (ten of them whole files of inventory or repository-tree tests, five partial), each with its reason in
`tests/regression/compat/allow-v1.3.0.json`), the v1.3.0 samples compile
against the current sources, and the API, schema and manifest supersets hold
against the frozen 1.2.0 **and** 1.3.0 captures. One install-time floor
moves, and the bytes of font-embedding documents move once — see **Upgrade**.

## Highlights

### Right-to-left documents — `direction`

`<Document direction="auto">` (`'auto' | 'ltr' | 'rtl'`, the engine's
`TextDirection`) resolves every paragraph's base direction from its first
strong character (UAX #9 P2–P3): an Arabic or Hebrew paragraph is set from the
right margin, its neutral punctuation follows the paragraph, its lines wrap on
the right. `<Paragraph direction>` overrides it per block; the DocSpec twin is
the top-level `direction` field (the 19th, appended after `creationDate`) and
the paragraph opt of the same name, both described in the schema with the
engine enum. Omitted, the output is byte-identical to earlier releases.

Every right-to-left run carries its logical text as an untagged
`/Span /ActualText` (engine ledger C27), so extraction and copy-paste return
the source string; `layout.actualText: false` opts out — a compatibility
switch, deliberately `layout`-only. Sample: `samples/text/rtl-direction.tsx`
(Arabic and Hebrew through `resolveFonts({ ar, he })`).

### Spot colours

`print.spotColours` declares named inks with a process alternate
(`{ name: 'Brand Blue', alternate: [100, 44, 0, 0] }` — four CMYK percentages
or three RGB values); a colour value `{ spot: 'Brand Blue', tint?: 0.5 }`
paints through a `/Separation` space and `{ inks: { 'Brand Blue': 1,
Varnish: 0.3 } }` through a `/DeviceN` mix, on every painted colour position —
headings, paragraphs, links, table zebra and borders, chart palettes, and one
ink per bar through `ChartSeries.colors`. One position is not painted: an
outline bookmark colour (`/C`) is an RGB triple by the PDF specification, so
the schema types `outline[].color` as `$defs.processColor` (hex, RGB or CMYK
only) and the engine's refusal of a spot value there is `E_INPUT`. The `Color`
type and the schema's `$defs.color` gain the two object forms (`spot` must be
non-empty); `print.spotColours` is described in the schema. Two lint rules
carry the engine's throws verbatim, one tier earlier: `L_SPOT_UNDECLARED` (an
ink the document does not declare) and `L_SPOT_INK_MIX` (a mix across CMYK and
RGB alternates); `L_PRINT_BOXES` now also carries the declaration errors (empty
or duplicate name, alternate out of range), `L_CMYK_INTENT_MISMATCH` counts a
CMYK-alternate ink as CMYK content, and `toErrorEnvelope` classifies the
engine's colour throws as `E_INPUT`. Sample:
`samples/layout/print-spot-colours.tsx`, a PDF/X-4 sheet that
`validatePdfX()` accepts.

Two statements the audit corrected while it was at it: `layout.colors` (the
engine's `PdfColors` palette) is accepted and forwarded but read only by the
engine's table-report builder, never by the block-flow renderer this package
drives — it is no longer listed as a colour position; and `tagged: true` is the
engine's default claim, PDF/A-2b, byte-identical to `'pdfa2b'`, while the
three PDF/A lint rules evaluate the string levels only — name the level to get
the pre-flight (1.4.1 widens the rules).

### One file, both claims — PDF/A-2 + PDF/X-4

`tagged="pdfa2b"` (or `"pdfa2u"`) now combines with `pdfx="pdfx4"`: the XMP
carries both identifications, the structure tree and the TrimBox coexist, the
output intent serves both standards. `L_PDFX_TAGGED_CONFLICT` keeps its code
and narrows to the two levels the engine still refuses — PDF/A-1 (PDF 1.4,
no PDF/X-4) and PDF/A-3 (embedded files, which PDF/X forbids) — with the
engine's two per-level messages. Sample:
`samples/layout/print-dual-pdfa2b-pdfx4.tsx`; the conformance corpus runs the
dual file through veraPDF **and** `validatePdfX()`.

### Charts — per-value colours, optional labels

`ChartSeries.colors` paints one colour per value on the four bar kinds
(`bar`, `barH`, `stackedBar`, `stackedBarH`; the other kinds ignore it, the
legend swatch keeps `color`); `L_CHART_SERIES_COLORS` is the engine's
length-mismatch throw one tier earlier. `ChartSeries.label` is optional — an
unnamed series is listed as `Series N` in the legend and in every lint
message. The schema's series `required` list is `['values']`.

### JPEG 2000 images

`<Image data>`, `['img', { data }]` and `watermark.image` accept a JP2 file
or a raw J2K codestream, detected from the magic bytes and passed through as
`/JPXDecode` under a `%PDF-1.5` header — never decoded, exactly as the DCT
data of a JPEG. Under PDF/A the claim's rules apply, and `L_PDFA_JPX_IMAGE`
says so before the engine's `PDFA1_JPX_IMAGE` (any JPEG 2000 under PDF/A-1)
and `PDFA_JPX_IMAGE` (channels not 1, 3 or 4, or an opacity channel, under
PDF/A-2+) diagnostics do; both throw under `layout.strict`. The channel facts
come from the engine's own `parseJPX`, called inside the bridge. Sample:
`samples/media/image-jpx.tsx`; the fixtures of `scripts/lib/jpx-fixture.ts`
are shared by the tests, the sample and the corpus.

### 32 Unicode scripts

Gujarati (`gu`), Gurmukhi (`pa`), Kannada (`kn`), Malayalam (`ml`) and Odia
(`or`) join through `resolveFonts` on the engine's Indic shaping engine;
`samples/fonts/scripts-32.tsx` replaces `scripts-27` and shows the ten scripts
of 1.8.0 and 1.9.0 together, with a danda-closed Gurmukhi and Odia line and a
Kannada cluster placed as HarfBuzz places it.

### Thirteen diagnostic codes

`TEXT_GLYPH_NOT_COVERED` — a character no registered font covers used to
render as a box or a `?` in silence; it now reaches `layout.onDiagnostic` as
a warning and throws under `layout.strict`. There is deliberately no lint
tier: deciding which font covers a character is the engine's routing. The
three others — `PDFA1_JPX_IMAGE`, `PDFA_JPX_IMAGE` (mirrored by
`L_PDFA_JPX_IMAGE`) and `PDFA_GLYPH_WITHOUT_UNICODE` (the engine's PDF/A-2u
ToUnicode self-check) — complete the thirteen.

### Agents

`doctor()` grades a 1.8.x engine down (floor 1.9.0, probe `resolveBidiLevels`
newest-first); `capabilityManifest().contract.engine` is `^1.9.0`; the
manifest lists the 41 rules and the 19 fields; the schema `$id` carries
1.4.0. `toErrorEnvelope` is total: a thrown value with no primitive
conversion (`Object.create(null)`, a hostile `{ toString: 1 }`) is described
by its object tag instead of making the envelope itself throw — found by the
new fast-check property tier.

## Upgrade

No breaking API change: nothing removed, renamed or newly required. Drop-in
replacement for v1.3.0 for every program that does not compare bytes of
font-embedding documents. Two things move with the engine, by the rule
`SECURITY.md` states — the `pdfnative` peer floor follows the engine minor
(install-time, step 1), and three types widen (compile-time, step 7).

### Migrating from v1.3.0

1. **Upgrade the engine.** `pdfnative` ≥ 1.9.0 is required; `doctor()` says
   `1.8.x — this release needs >= 1.9.0` on an older peer.
2. **Rebaseline once if you compare bytes.** Every document that embeds a
   font changes bytes — the subset is lean and compact and its `/BaseFont`
   carries a six-letter tag (`ABCDEF+NotoSans-Regular`, bare under PDF/A-1),
   every line is one text object, right-to-left and reordered runs carry an
   `/ActualText` span; a document with a translucent watermark gains a page
   transparency group. Documents on base-14 fonts with none of those are
   byte-identical. The repository's baseline moved 10 samples to `since:
   1.4.0` (`fonts/fonts-prop*`, `layout/page-setup`, `layout/print-pdfx4`,
   `layout/watermark-header-footer`, `text/math`, `text/typography-engine`,
   `text/typography-french`, `layout/cmyk`, `charts/charts-v2`), renamed
   `fonts/scripts-27` to `fonts/scripts-32` and added four (15 entries at
   `since: 1.4.0`, 38 → 42); the 27 others are untouched
   (`tests/regression/baselines/samples.sha256.json`, provenance note).
3. **Strip the subset tag** where you match font names: `^[A-Z]{6}\+`.
4. **Expect `TEXT_GLYPH_NOT_COVERED`.** A character no registered font covers
   is a warning on `layout.onDiagnostic` and a throw under `layout.strict`;
   a strict pipeline that rendered boxes silently now stops — register a
   covering font or replace the character.
5. **New lint findings a document may trip:** `L_SPOT_UNDECLARED`,
   `L_SPOT_INK_MIX`, `L_CHART_SERIES_COLORS`, `L_PDFA_JPX_IMAGE`; and one it
   no longer trips: `L_PDFX_TAGGED_CONFLICT` with `pdfa2b`, `pdfa2u` or
   `true` (the engine's default claim is PDF/A-2b, so `true` + `pdfx4` is the
   joint claim).
6. **Repository tooling:** the publish gate runs `compat:previous` and needs
   the previous tag (`git fetch --no-tags origin
   +refs/tags/v1.3.0:refs/tags/v1.3.0` on a shallow clone); the main ruleset
   requires two more checks (re-import `.github/rulesets/main.json`).
7. **TypeScript consumers.** Three types widen with the engine pin; code that
   *reads* them may stop compiling under `strict`: `Color` admits
   `PdfSpotColor` and `PdfInkMix`, so a narrowing such as
   `typeof c === 'string' ? c : c[0]` needs an object branch;
   `ChartSeries.label` is `string | undefined`; `LintRuleCode` and
   `DocSpecField` gain members, so an exhaustive `switch` needs the four rules
   and `direction`. Code that only *passes* these values in is unaffected
   (`npm run typecheck:compat` compiles the 1.2.0 and 1.3.0 samples unchanged).
8. **Three limits now stated, none new:** `layout.colors` never reached the
   block-flow renderer; a PNG with an alpha channel (colour types 4 and 6) is
   refused by the engine (`parsePNG: …`, `E_INPUT`) — flatten it first; a spot
   colour on an outline bookmark is refused (`E_INPUT`; the schema says so).
